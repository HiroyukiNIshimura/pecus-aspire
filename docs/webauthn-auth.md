# WebAuthn（パスキー）認証リファレンス

パスキー認証・リカバリーコード・レート制限の実装仕様をまとめたリファレンスです。
実装の根拠となるコードを併記しているため、変更時はこの文書も更新してください。

## 1. 認証方式の概要

- ログインは **WebAuthn（パスキー）** を基本とする。組織ごとに認証方式を切り替えられる。
- 組織設定は `OrganizationSettings.AuthenticationMode`（`null` は「パスワード + パスキー」）。

| 値 | 意味 |
| --- | --- |
| `Password` | パスワードのみ |
| `WebAuthn` | パスキーのみ |
| `Both`（`null` を含む） | パスワード / パスキーの両方 |

- セッションは Redis（`ServerSessionManager`）で管理し、Cookie には `sessionId` のみを保存する。

### 1.1 認証方式の事前判定について

- 未認証で「そのユーザーがどの方式を使えるか」を返すエンドポイントは**提供しない**。
  組織の認証方式やパスキー登録有無を返すと、パスワード専用／パスキー専用の組織でアカウントの存在を判別できるため。
- 方式判定は `login/options`（パスキー）と `login`（パスワード）で行う。認証失敗時は、ユーザー不在・パスキー未登録・組織ポリシーによる拒否などの理由を区別できない汎用エラーを返す。`login/options` はポリシー拒否も「認証に失敗しました。」に統一する。
- 画面側では事前判定を行わず、ユーザーが選んだ方式（パスキー／パスワード）でそのまま認証を試みる。

## 2. レート制限

実装: [LoginRateLimiter.cs](../pecus.WebApi/Services/LoginRateLimiter.cs)（Redis の `INCR` + `EXPIRE` を Lua スクリプトで 1 回実行し、**固定ウィンドウ**で制限する）

- 加算と有効期限設定を同一スクリプトで行う。途中失敗で TTL の無いキーが残り、恒久的に 429 になる事故を防ぐため。

### 2.1 制限一覧

| エンドポイント | キー（`auth:ratelimit:` 配下） | 上限 | ウィンドウ |
| --- | --- | --- | --- |
| `POST /api/entrance/webauthn/login/options` | `options:{loginId}` | 20 回 | 5 分 |
| `POST /api/entrance/webauthn/login/verify` | `verify:{credentialId のハッシュ}` | 20 回 | 5 分 |
| `POST /api/entrance/webauthn/register/options` | `register-options:{token のハッシュ}` | 20 回 | 5 分 |
| `POST /api/entrance/webauthn/register/verify` | `register-verify:{credentialId のハッシュ}` | 20 回 | 5 分 |
| `POST /api/entrance/recovery/code` | `recovery:{loginId}` | **5 回** | **15 分** |

- ログイン ID 部分は小文字化して正規化される。クレデンシャルID・トークンは SHA-256 の先頭 16 バイトをキーに使う（長い値をそのままキーにしない）。
- キーは**クライアント IP ではなく、アカウント・クレデンシャル・トークン単位**で数える。画面は Server Action から WebApi を呼ぶため、送信元 IP は常にフロントエンドになり、IP 単位にすると全ユーザーが 1 つのバケットを共有してしまう（誰かの試行で全員が 429 になる）。また `X-Forwarded-For` はクライアントが任意に指定できるため、IP をキーにすると制限を回避できる。
- このため、同一 IP の複数ユーザーは互いに影響しない。逆に、同じアカウント（または同じクレデンシャル）への試行は、送信元が変わっても同じカウントを共有する。
- パスワードログイン（`POST /api/entrance/auth/login`）には現時点でレート制限がない。

### 2.2 429 になったときの考え方（重要）

- **固定ウィンドウ**のため、期限は「**最初の試行時刻 + ウィンドウ幅**」。最後の試行からではないので、連打しても待ち時間は延びない。
- **成功してもカウントは戻らない**（加算のみ）。上限に達したら、ウィンドウが明けるまで待つ必要がある。
- ウィンドウが明けるとキーが消え、カウントは 0 に戻る。

### 2.3 残り時間の確認（開発・運用）

バックエンド用 Redis のキーを直接見れば、残り回数と残り秒数が分かる。

```bash
# コンテナ名は Aspire 起動ごとに変わる（redis-xxxx）
RC=$(docker ps --format '{{.Names}}' | grep -E '^redis-' | head -1)
PW=$(docker exec "$RC" printenv REDIS_PASSWORD)

# キー一覧
docker exec "$RC" redis-cli -p 6380 -a "$PW" --no-auth-warning KEYS 'auth:ratelimit:*'

# 残り回数と残り秒数
docker exec "$RC" redis-cli -p 6380 -a "$PW" --no-auth-warning GET 'auth:ratelimit:recovery:<loginId>'
docker exec "$RC" redis-cli -p 6380 -a "$PW" --no-auth-warning TTL 'auth:ratelimit:recovery:<loginId>'
```

- Aspire の Redis は **TLS ポート 6379** と **非 TLS ポート 6380**（`--requirepass`）で動く。コンテナ内からは 6380 を使う。
- クレデンシャルID・トークン由来のキーはハッシュ（32 桁の 16 進数）になる。

### 2.4 開発環境で即座に解除する

待たずに試したい場合は、該当キーを削除すればリセットされる（**開発環境のみ**）。

```bash
docker exec "$RC" redis-cli -p 6380 -a "$PW" --no-auth-warning DEL 'auth:ratelimit:recovery:<loginId>'
```

## 3. リカバリーコード

実装: [RecoveryCodeService.cs](../pecus.WebApi/Services/RecoveryCodeService.cs)

- **1 回限りの使い捨て**。1 回の発行で **10 個**（`CodeCount = 10`、10 文字を `XXXXX-XXXXX` 形式で表示）。
- DB には平文を保存せず、**HMAC-SHA256 ハッシュのみ**を保存する（鍵は `Pecus:WebAuthn:RecoveryCodePepper`）。
- `Development` 以外の環境では pepper の設定が**必須**。未設定、または `CHANGE_ME_RECOVERY_CODE_PEPPER_IN_PRODUCTION` のままの状態で起動すると `Program.cs` が起動時に例外を投げる。秘密管理基盤などから環境変数 `WEBAUTHN_RECOVERY_CODE_PEPPER` を生成スクリプトの実行環境に渡し、設定ファイルを生成する場合は、その環境変数を設定した状態で `node scripts/generate-appsettings.js -P` を実行する。生成後は WebApi を再起動して反映する。pepper と生成済み設定ファイルは秘密情報として保護し、リポジトリへ登録しない。`Development` 環境のみ既定値で動作する。
- 起動できないイメージを配布しないよう、`-P` での生成時にも検証する。pepper が未設定・`CHANGE_ME` 始まり、`RpId` が `localhost` のまま、または `Origins` に `https` 以外が含まれる場合は**生成を中止**する（[generate-appsettings.js](../scripts/generate-appsettings.js)）。
- `RpId` / `Origins` は、生成時点のフロントエンドURL（`FRONTEND_URL`、未指定なら `config/settings.base.prod.json` の `urls.frontend`）から自動導出する。明示指定は `WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGINS`（カンマ区切り）/ `WEBAUTHN_RP_NAME` を使う。デプロイ手順の詳細は [DEPLOY_OVERVIEW.md](../deploy/DEPLOY_OVERVIEW.md) を参照。
- 平文を返すのは**発行レスポンスの 1 回だけ**。画面を閉じると再表示できない。

### 3.1 発行・消費のルール

| 操作 | 挙動 |
| --- | --- |
| 発行 / 再発行（プロフィール画面） | 既存コードをすべて削除し、新しい 10 個を発行 |
| 管理者リセット（セットアップトークン） | ユーザーが新しいパスキー登録を完了した時点で、既存パスキーを削除し、全セッションを失効させ、既存コードを削除して新しい 10 個を発行 |
| ログイン済みユーザーがパスキーを追加 | コードは発行しない（必要な場合は再発行 API を使う） |
| **リカバリーコードで復旧** | **使用したコードのみ消費**。残りはそのまま有効。**残り 0 のときだけ**新しい 10 個を自動発行 |

- 復旧時は、使用したコードの消費に加えて**全セッションを失効**させる（他端末はログアウト）。
- パスキー・リカバリーコード・デバイス状態などの DB 更新は DB トランザクション内で実行する。一方、登録チャレンジは DB トランザクション開始前に Redis で消費され、リカバリートークンの消費やリフレッシュトークン/JWT の失効も Redis 上で行われるため、いずれも DB トランザクションには参加しない。したがって、登録処理が失敗すると、DB がロールバックされてもチャレンジ／トークンの消費やセッション失効は取り消されない場合がある。DB と Redis をまたぐ処理全体の原子性は保証されない。
- 残りが 2 個以下になると、プロフィール画面の再発行ボタン横に警告を表示する。
- パスキー専用の組織でリカバリーコードが残っていない場合、**最後の 1 件のパスキーは削除できない**（先に発行を促すエラーを返す）。削除すると管理者リセット以外にログイン手段が無くなるため。
- パスキー専用の組織では、認証済み・管理操作としてのパスワード変更、および管理者／バックオフィスからのパスワードリセットメール・パスワード設定メール再送を 400 で拒否する（パスキー登録リセットを案内する）。
- 未認証の `POST /api/entrance/password/request-reset` は、アカウントの存在や組織の認証方式を推測されないよう、パスキー専用組織のユーザーでも常に汎用の成功応答を返し、メールは送信しない（1.1 と同じ理由）。パスワードを忘れた画面には、**パスキー専用の組織では**メールが届かないことと `/recovery`（リカバリーコード）・管理者リセットへの導線を常時表示する（`Both` の組織ではパスキー登録済みでもメールが届く）。
- パスキーを許可していない組織（`Password`）では、パスキー登録リセットメールを 400 で拒否する。発行しても登録画面で利用できないため。
- 「作り直す」操作はログイン後のプロフィール画面（`/profile` → セキュリティ → パスキー）から行う。登録完了画面は未ログイン状態のため、匿名で再発行できる API は用意していない。
- パスキー登録時の `deviceId` はクライアント指定値のため、**自ユーザーの端末のみ紐づける**（他ユーザーの端末 ID や存在しない ID を指定された場合は紐づけずに登録を継続する）。他ユーザーの端末が紐づくと、一覧での端末名参照や削除時のセッション失効の起点になるため。
- パスキーの登録上限は **10 件**（`WebAuthnCredentialService.MaxCredentialsPerUser`）。上限判定は認証済みの追加登録時のみ行い、**管理者リセットとリカバリー登録では免除する**（上限に達した状態でも復旧経路を塞がないため）。管理者リセットは登録完了時に既存パスキーを削除するので完了後は 1 件、リカバリーは既存を残したまま 1 件追加する。
- 管理者リセット・リカバリーの登録では、既存クレデンシャルを `ExcludeCredentials` に含めない（同じ認証器で再登録した際に `InvalidStateError` となり復旧できなくなるため）。
- 組織の認証方式を `WebAuthn` に変更すると、対象組織の有効ユーザーの**全セッション（デバイス・リフレッシュトークン・JWT）を失効**させる（[SessionRevocationService](../pecus.WebApi/Services/SessionRevocationService.cs)）。パスワードで確立済みのセッションはリフレッシュで延命されるため、失効させないと方式変更が既存セッションに作用しない。切替後は全ユーザーがパスキーで再ログインする。失効は組織設定の更新コミット**前**に実行し、失効に失敗した場合は方式が変わらないまま再試行できるようにしている（逆に、失効後にコミットが競合した場合は方式が変わらなくてもセッションだけが失効し得る）。失効処理の途中で確立されたパスワードセッションを取りこぼしても、**リフレッシュ時に組織の認証方式を再判定**するため（アクセストークンの有効期限まで）、パスワード由来のセッションが延命されることはない。リフレッシュトークンには発行時の認証方式（`password` / `passkey`）を保持し、その方式が許可されていない組織では 401 を返す。方式を保持していないトークン（本機能の導入前のトークンや、Redis 消失時に DB から復元したトークン）は、**両方の方式を許可している組織でのみ**許可する（安全側に倒し、制限のある組織では再ログインを求める）。
- パスワードが未設定のユーザー（パスキー専用の組織）は、**現在のパスワードなしでメールアドレス変更を申請できる**。本人性はログイン済みセッションと新しいメールアドレス宛の確認メールで担保する。パスワード設定済みのユーザーは従来どおり現在のパスワードが必要。
- プロフィール画面から追加したパスキーは**現在の端末に紐づく**（`UserCredential.DeviceId`）。そのパスキーを削除すると、紐づく端末のセッションも失効する。端末 ID はクライアント指定値のため、サーバー側で自ユーザーの端末であることを検証する。リフレッシュ時は同じ端末識別子の Device 行を**再利用**するため、紐づけはリフレッシュをまたいで維持される。ログイン時の「新しいデバイス」判定は従来どおり行う（リフレッシュでは通知しない）。
- `/passkey-setup`（管理者リセット・リカバリーコード）からの登録は未ログインのため端末 ID を送らず、**端末には紐づかない**（削除しても端末セッションは失効しない）。

### 3.2 二重利用の防止

- **コードの消費は条件付き更新**（`UsedAt IS NULL` のときだけ更新）。同じコードで同時に複数リクエストが来ても、成功するのは 1 件だけ。2 件目以降は 401 を返す。
- リカバリートークンは Redis の `GETDEL` で消費する。登録完了時に失効済みだった場合は警告ログのみ残し、処理は継続する（コード側の条件付き更新で二重利用を防ぐ）。
- セッション失効時の DB 上のデバイス／リフレッシュトークン状態更新は DB トランザクションの対象だが、Redis 上のリフレッシュトークン削除・JWT ブラックリスト登録は対象外。Redis 側の処理に失敗した場合は DB がロールバックされるが、既に完了した Redis 操作は取り消されない。部分失敗時は再度セットアップ／リカバリーを行う必要が生じる場合がある。

### 3.3 未使用件数

- `GET /api/profile/credentials/recovery-codes` → `{ hasUnusedCodes, unusedCodeCount }`
- パスキー登録（セットアップ / リカバリー）のレスポンスにも `unusedRecoveryCodeCount` が入る。
  新規発行した場合は発行数（10）、残りを使い続ける場合はその残数。
